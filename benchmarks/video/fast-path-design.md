# Source timing and bounded fast decode design

Status: measured local metadata and synthetic CPU experiments; proposed runtime
interfaces only. Production decoder, serving processes, GPUs, uploads, models,
rules and verdict behavior were not changed by this work.

Implementation follow-up: root subsequently authorized an additive optional
`forte.video.batches` module. It now implements the in-memory identity/RGB batch
and grouped boundary interfaces below. The existing production decoder remains
unchanged. The optional module has synthetic correctness checks; the timings in
this report remain isolated prototype measurements, not timings of the new
module or an end-to-end deployment.

## Source timestamp resolution

`source-timing-aggregate.json` was generated by local **packet demux only**. No
supplied image pixels were decoded, displayed or sent to a model. All 42 source
file stat identities remained unchanged.

| Measurement | Aggregate result |
|---|---:|
| Successfully read sources | 42 / 42 |
| Video time base | 1 / 19,200 seconds for all 42 |
| Timestamp clock tick | 0.052083 milliseconds |
| Presentation packets / declared frame counts | 43,230; match in all sources |
| Adjacent PTS interval 1 / 30 s | 43,093 intervals |
| Adjacent PTS interval 1 / 15 s | 95 intervals |
| Sources containing the longer interval | 37 / 42 |
| Duplicate / missing presentation timestamps | 0 / 0 |
| Source duration range | 11.633333 to 142.533021 seconds |
| Maximum source frame count | 4,273 |
| Consecutive keyframe gap | 0.9 to 1.1 seconds |
| Maximum source-PTS rounding error when rendered to milliseconds | 0.333334 milliseconds |

The fine clock tick is not the image observation interval. The available images
are usually 33.333 milliseconds apart and sometimes 66.667 milliseconds apart.
`frame_index / 30` is wrong after a missing image. Every feature, boundary,
evidence frame and UI time label must retain the actual source PTS.

Keep `timecode_sec` and evidence `timestamp_sec` as the actual normalized source
timestamp. Render UI strings as `HH:MM:SS.sss`, using integer source ticks and
rounding only at display. For a boundary, preserve the last supported absence,
first supported presence and adjacent real PTS. Display precision of three
decimals cannot establish one-millisecond event accuracy. A visible onset lies
between observations unless the underlying action definition supports a more
specific source frame.

## Local synthetic CPU results

`synthetic-decode-cpu.json` records two passes per case on a Ryzen 5 8645HS,
Windows 11, Python 3.14, PyAV 19.0.1. The generated H.264 test pattern is
464 × 848, 30 fps, 4,276 frames / 142.533 seconds, with B frames and one-second
keyframes. It contains no supplied footage. Times exclude fixture generation.

| Case | Median seconds |
|---|---:|
| Decode and inspect PTS, one slice thread | 3.233 |
| Decode and inspect PTS, two frame threads | 1.997 |
| Decode and inspect PTS, four frame threads | 1.285 |
| Decode all native frames to 256² RGB byte batches, four frame threads | 3.962 |
| Decode once; convert 8 fps to 256² RGB byte batches | 1.934 |
| Decode once; convert 8 fps with aspect-preserving 256² letterbox | 1.910 |
| Decode once; write 2 fps as original-resolution JPEG quality 95 | 5.129 |
| Seek and refine four 0.5-second brackets to native frames and 256² RGB | 0.079 |

The seek experiment decoded 107 frames including keyframe preroll and converted
64 native frames. Every returned PTS exactly matched the expected synthetic
packet index. This is a useful regression fixture, not an event-quality result.

The measurements support streaming RGB batches without intermediate JPEGs.
They do not prove deployed CPU throughput, GPU encoder throughput, model quality,
upload performance or a sub-ten-second end-to-end service. A queue, slow uplink,
or expensive encoder can dominate the result.

## Proposed runtime contract

Use a new iterator rather than expanding `FrameRef` to mean transient pixels.
Existing `FrameRef` continues to identify an original-resolution JPEG suitable
for evidence. Proposed internal types:

```python
SourceFrameMeta(
    frame_id, content_hash, source_pts,
    time_base_num, time_base_den, source_origin_pts,
    pts_sec, next_pts_sec, width, height, applied_rotation_deg,
)
FrameBatch(
    frames: tuple[SourceFrameMeta, ...],
    pixels,  # uint8 RGB [B, 256, 256, 3] or explicitly typed device tensor
    view_ids, normalized_source_boxes, transform_manifest,
)

iter_frame_batches(
    asset, *, batch_size=32, mode="native", sample_fps=None,
    target_size=(256, 256), aspect_policy,
    deadline_monotonic, cancel, thread_count=4,
) -> Iterator[FrameBatch]

refine_source_brackets(
    asset, requests, *, source_index,
    batch_size=32, deadline_monotonic, cancel,
) -> Iterator[FrameBatch]
```

`frame_id` remains the current SHA-256 identity derived from source content
hash, source PTS and stream time base. Add the integer origin to the new metadata
so temporal operations avoid rounded decimal start strings. `next_pts_sec`
requires one-frame lookahead; EOF uses an explicitly marked source-duration end
bound, not an invented following frame.

Frame batches must be monotonic within each segment, use the actual PTS, include
the actual final source frame and flush delayed B frames. Similar or identical
images must never be deduplicated as a timestamp optimization. A four-thread
frame decoder is a measured candidate; retain a bounded configured count and
test B-frame flush, cancellation and seek behavior before changing production.

## Bounded pipeline

1. Reuse the upload's incremental SHA-256 after owned-file finalization. Probe
   metadata in the worker; leave the upload acceptance path short. Keep current
   FFprobe until a separately tested metadata replacement exists.
2. Decode video once with frame threading. Convert selected/native source
   frames directly through PyAV/libswscale to the frozen encoder's RGB 256²
   input. Lock the aspect and ROI policy with training; global letterboxing
   preserves the full source view, but changing the tower's trained preprocessing
   needs validation. Always apply source rotation before defining view boxes.
3. Feed a queue of at most two batches to a warm GPU encoder. Batch 32 has about
   6.29 MB of RGB bytes; two batches need about 12.58 MB plus decoder surfaces and
   staging. Do not retain the entire approximately 840 MB RGB clip. Retaining
   all 4,273 × 768 BF16 embeddings costs only about 6.56 MB per view.
4. Use backpressure: the decoder cannot outrun the encoder indefinitely. Keep
   pinned staging buffers alive until the asynchronous GPU copy completes.
   Overlap CPU decode/resize, host-to-device transfer and GPU encoder batches.
   Do not serialize raw pixels through JSON, JPEG or HTTP between colocated
   components.
5. Give the temporal head actual timestamp gaps and explicit visibility masks.
   Native-frame global coverage is preferred if measured encoder throughput
   permits it. A 4/8-fps coarse path must earn its selection with reviewed
   short-event recall; coarse sampling alone cannot justify source-frame onset.
6. Group overlapping refinement brackets and brackets sharing a keyframe.
   Seek to the preceding keyframe once per group and decode every original PTS
   through the group's upper boundary plus one neighbor. Require the complete
   expected PTS set. Retry an earlier indexed keyframe on a seek overshoot;
   never replace a missing exact frame with the nearest convenient sample.
7. Refine physical facts and onset/end support at native resolution in time.
   A nearest-source-frame snap only changes coordinates; it does not prove an
   event boundary. Preserve an uncertainty bracket when the supporting semantic
   decision is unclear. Unknown training spans remain masked.
8. Apply existing verified fact/rule/event logic. Only then seek/batch retrieve
   the selected 1–3 original evidence frames per event and JPEG-encode them.
   Avoid the current evidence path's repeated full-clip decode for this new
   fast path; retain source hash, exact PTS and immutable evidence validation.

The current `decode_frames` intentionally writes full-resolution JPEGs. Reusing
it for thousands of frozen-encoder inputs retains avoidable conversion,
filesystem and image-reload cost. The proposed iterator is an additive path;
the tested existing evidence contracts remain available.

## Dense boundary refinement

Requests should carry `(event_id, lower_source_pts, upper_source_pts,
required_fact_ids)`. The interval must include the last supporting negative and
first supporting positive from the coarse/native temporal decision, plus the
context required by that event's physical definition. Merge requests before
decoding. Use `container.seek(lower_pts, stream=stream, backward=True,
any_frame=False)` followed by sequential decode, as documented by
[PyAV's container API](https://pyav.basswood.io/docs/stable/api/container.html).
Validate returned source PTS against the index and preserve ordering across
segment boundaries explicitly.

The source metadata's at-most-1.1-second keyframe gaps make local refinement
promising; they do not imply zero seek cost. A bounded refinement budget must
not silently discard additional events. Exceeding the verified budget must
surface an explicit processing outcome under the existing decision policy.

## Ten-second measurement boundary

Measure from the first client upload byte to the last byte of completed jury
JSON, with cache disabled. Required stages include body transfer, durable
acceptance, queueing, probing, decode/preprocessing, GPU features, temporal head,
boundary refinement, evidence encoding, result publication and result transfer.
Streaming permits overlap; do not simply add independent isolated throughput
benchmarks and call that observed latency.

For native coverage of the maximum 4,273 source frames, a six-second vision
allocation needs at least 712 frames/second including copies. Matching the
measured 3.962-second CPU producer needs about 1,079 encoder frames/second.
Additional ROI views multiply the encoder work. These are capacity requirements,
not measured model throughput.

Upload time is an independent lower bound: 30 MB takes 2.4 seconds at an ideal
100 Mbit/s before protocol overhead. A universal sub-ten-second claim cannot
ignore the client's effective uplink or time spent queued. Reserve warm model
capacity and measure the real route before declaring the target met.

## Optional hardware decoding

CPU frame threading is the first measured implementation candidate. PyAV exposes
hardware decoding through `HWAccel`, but device enumeration alone does not prove
the deployed build/driver works. Its
[official hardware-decode example](https://github.com/PyAV-Org/PyAV/blob/master/examples/basics/hw_decode.py)
states that Linux CUDA decoding needs an appropriately built FFmpeg. A GPU-owned
decode path should retain surfaces on the device and validate its tensor
interop and RGB preprocessing, rather than download and re-upload every frame.
Use explicit hardware failure during benchmarking so software fallback cannot
be misreported as NVDEC performance. No hardware decoding was invoked here.

## Next implementation checks

Before deployment: synthetic VFR/rotation/B-frame/tail cases, correct batch
lifetimes and backpressure, exact seek/frame ID equality, cancellation while
blocked on a full queue, process termination on a stuck decoder, and bounded
memory. Then benchmark the deployed CPU plus selected frozen encoder on
generated fixtures. Quality selection additionally requires reviewed source
frame boundaries and held-out event/negative checks; these timing experiments
cannot supply that evidence.

## Implemented optional interface notes

`iter_rgb_batches(asset, sample_fps=None, ...)` selects every native source frame;
a positive given rate selects nearest real frames, prefers earlier ties and
always includes the actual last source frame. Batch pixels are tightly packed
RGB uint8 bytes with `batch.shape == (B, H, W, 3)`. `frame_pixels(i)` returns a
zero-copy memoryview. Pixel bytes are excluded from object reprs.

`SourceFrameIdentity` carries the integer source origin and next source PTS, the
canonical time-base string and numerator/denominator, normalized seconds,
stream/job/content identity, original upright dimensions, source rotation
already applied to pixels, and keyframe state. The final frame has an explicit
`source_end_bound_sec`, while `next_source_pts` and `next_pts_sec` remain null.
`source_frame_id(hash, pts, num, den)` lets training validate identities without
inventing media paths or assets.

Batch completion fields distinguish selection mode, requested count,
segment-delivered count, cumulative delivered count, decoded source count,
segment completion, full-source completion and actual-tail inclusion. Full
completion is withheld until the decoder has flushed B frames and checked any
declared native frame count. These fields describe feature coverage, not scene
visibility or completion of a banking procedure.

`rgb_transform_recipe(...)["sha256"]` identifies output geometry, resize/color
conversion, rotation policy and installed PyAV/libswscale/Pillow versions.
`RGBFrameBatch.transform_sha256` binds each batch to that recipe. Tower
normalization remains the encoder's responsibility. A caller must lock the
recipe in its feature specification; libswscale pixels are not claimed to be
identical to a different official processor backend.

`iter_boundary_batches` merges overlapping requests, seeks to preceding indexed
keyframes and validates the exact native PTS set. It accepts a complete native
identity chain or builds a bounded metadata-only packet index. Distinct
nonoverlapping brackets sharing a keyframe currently remain separate seeks;
combining those is a later optimization. Bracket completion never claims
full-video coverage.

Readers default to spawn-isolated hard cancellation/deadlines with bounded
batch messages and pipe backpressure. An outer supervised process may select
`use_subprocess=False` to avoid pipe copies. Exhaust readers or use
`contextlib.closing` when stopping early so codec processes and slots are freed.

`materialize_evidence_frames` validates selected source identities and source
SHA-256, then uses the existing decoder to create real owned JPEG FrameRefs and
requires exact ID equality. It creates no fake path-bearing records. This
adapter conservatively retains one full forward decode for selected evidence;
it does not yet implement grouped JPEG evidence seeks. Call it once for all
events, then pass its actual FrameRefs to the existing evidence validator.

## Optional exact-seek evidence follow-up

The separate `forte.video.evidence_seek.materialize_evidence_frames_seek` now
provides the faster alternative without editing the frozen feature decoder or
the default JPEG decoder. It accepts at most three selected canonical source
identities and the completed full native ledger. Selected frames sharing a
preceding source keyframe share one seek/decode group. It validates source
SHA-256, native units/origin/identity, exact interval PTS and the original
metadata retained by the feature pass. Only selected full-resolution decoded
frames reach the original JPEG writer; encoder RGB, letterboxing, crops and
overlays are not used. Each actual FrameRef points into a private operation
directory and carries its JPEG SHA-256. Cancellation, hard deadlines, actual
preroll, decoded-frame and JPEG-byte limits are enforced. No automatic
full-forward retry exists.

`synthetic-seek-evidence-cpu.json` compares three evidence frames from the
generated 142.533-second fixture. The native index is retained from a prior
pass and its setup time is reported separately. Grouped direct seeks took a
median **0.159 seconds**, compared with **2.827 seconds** for full-forward
materialization. Spawn-isolated seeks took **0.708 seconds**, including process
startup on this Windows host. The two seek groups decoded 36 original frames;
all three frame IDs and JPEG hashes exactly equaled full-forward outputs.
These are CPU evidence-stage results, not whole-service or GPU measurements.

Small correctness fixtures also compare exact JPEG hashes across VFR, B frames,
nonzero source origins and orthogonal rotation, and exercise private-output
cleanup after limits, deadlines and cancellation. `batches.py`, `decode.py` and
`probe.py` were preserved during this follow-up so frozen feature code hashes
remain valid. This helper can ship independently in a later source bundle.
