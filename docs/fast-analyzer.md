## 1. Архитектура

```
POST /api/v1/analyze (.mov) ──► API (FastAPI) ──► очередь заданий (PostgreSQL, аренда/таймауты)
                                                     │
                                       worker ◄──────┘  forte.fast.service.FastPipeline
                                         │ 1. декодирование видеоряда (PyAV, 2 кадр/с, без звука)
                                         │ 2. разметка сцены: модель находит стол, ноутбук, сейф, дверь,
                                         │    стул кассира и стул посетителя (bbox, один раз на видео)
                                         │ 3. посекундные состояния: кадр целиком + увеличенные фрагменты
                                         │    (экран ноутбука, поверхность стола, стулья) — по одному
                                         │    короткому вопросу на фрагмент, параллельно (до 64 запросов)
                                         │ 4. детерминированные правила по временной шкале состояний
                                         │ 5. проверка двери: попиксельное сравнение области двери
                                         │    с первым кадром после входа кассира
                                         │    допущенный профиль: VLM проверяет кандидатов перед ответом
                                         │ 6. сборка ответа: тип, таймкод, описание, норма, 1–3 JPEG
                                         ▼
                       локальный vLLM 0.31 (OpenAI-совместимый, внутренняя сеть Docker)
                       Qwen3-VL-30B-A3B-Instruct, bf16, 1×A100 80 GB
GET /api/v1/jobs/{id} ◄── неизменяемый опубликованный результат (processing | done | failed)
```

* **Локальность.** Все модели работают внутри развёрнутого стека; видео, кадры и описания не передаются
  во внешние сервисы. После загрузки весов интернет не нужен (`HF_HUB_OFFLINE=1`).
* **Модель.** [Qwen/Qwen3-VL-30B-A3B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct),
  лицензия Apache-2.0 (коммерческое использование разрешено). MoE-архитектура (~3B активных параметров)
  даёт качество крупной модели при скорости небольшой.
* **Звук и лица.** Звук не декодируется; лица не распознаются и не идентифицируются (в промптах запрещено
  описывать внешность, роли определяются только по положению у стола).

## 2. Почему так

Обучающих видео 40, типы нарушений не размечены, а финальное видео снято под другим углом. Поэтому решение
не обучается на конкретных роликах, а опирается на **проверяемые визуальные факты** (кассир на месте или нет,
что на экране ноутбука, что лежит на столе, открыта ли дверь) и **правила, вытекающие из нормативных актов**.
Ключевые находки при разработке:

* один большой вопрос о кадре даёт много ошибок; **короткий вопрос по увеличенному фрагменту** — почти без
  ошибок (например, «экран блокировки / рабочее приложение / закрыт» — 8 из 8 верно);
* стеклянные стены кабинета: люди за стеклом не должны считаться находящимися в кассе;
* положение объектов определяется моделью на каждом видео заново; качество при реальной смене камеры
  всё равно требует отдельной проверки видимости и зон.

(`disabled_types`), чтобы не давать ложных срабатываний.

## 4. Принцип сопоставления «норма — нарушение — фрагмент»

Каждое правило задаёт: (1) наблюдаемое условие (например, «кассир отсутствует на рабочем месте до конца записи
или вышел из кабинета» **и** «на экране ноутбука рабочее приложение»), (2) опорный момент (таймкод — момент,
когда кассир покинул рабочее место / подошёл следующий клиент / принята сумка и т. п.), (3) норму с пунктом.
В ответе API описание содержит: что видно → почему это может быть нарушением → документ и пункт с цитатой.
Кадры-доказательства — исходные кадры в момент события и ±1 с.

## 6. Ограничения и известные ошибки

* **Пропускаемые сейчас сценарии:** приём денег без удостоверения личности (на 464 px синие купюры и
  удостоверение неразличимы), ключ, оставленный в замке сейфа, пропуск проверки на детекторе подлинности,
  перекладывание пачек в сейф без пересчёта, неполная выдача суммы клиенту.
  Шестой пропуск остаётся неидентифицированным и требует локального разбора с командой.
* **Возможные ложные срабатывания:** светлый предмет на столе может быть принят за стакан; человек,
  стоящий в дверях, — за постороннего.
* Таймкод нарушения «по бездействию» (ушла, не заблокировав компьютер) ставится на момент ухода с рабочего
  места; разметка организатора иногда указывает момент выхода из кабинета (разница 3–5 с).
* Проверка двери требует, чтобы запись начиналась до входа кассира (дверь на первом кадре закрыта).
* Не проверяются данные, невидимые на видео (проводки, сверки, суммы в документах).
* Технический сбой не превращается в «нарушение не обнаружено»: задание получает статус `failed`.
