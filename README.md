# Forte Panopticon

Кассиру хватает работы. Проверяющему тоже. Мы сделали сервис, который находит в видео признаки возможных нарушений кассовой дисциплины и показывает, где стоит присмотреться: таймкод, исходные кадры и нормативное основание.

**Видим суть. Решаете вы.** Проект для кейса ForteBank на Datathon 26.

![Баннер команды: Видим суть. Решаете вы.](docs/assets/banner.png)

**[Открыть демо](https://hackathon.wezseo.me)** · **[API для жюри](https://forte-review-wd88a7vvt.gobrev.dev)** · **[Презентация](presentations/datathon/output/FORTE-Panopticon-Datathon-2026.pdf)**

## Что умеет

1. Принимает `.mov` через интерфейс или API и показывает ход обработки.
2. Сообщает, найдены ли признаки нарушения.
3. Для каждого события собирает тип, время, объяснение, нормативный источник и 1-3 исходных JPEG-кадра.
4. Позволяет перейти к фрагменту и подтвердить или отклонить находку вручную. Решение человека сохраняется отдельно от ответа модели.

Модели работают внутри развёрнутого сервиса. После подготовки весов и зависимостей для анализа не нужен интернет. Звук и идентификация лиц не используются.

## На что смотрим

В основном профиле предусмотрены восемь типов возможных событий:

| Событие | Что проверяем по видео |
| --- | --- |
| Незаблокированная рабочая станция | Кассир ушёл, рабочее содержимое осталось на экране |
| Ценности без присмотра | Кассир покинул место, наличные или ценности остались на столе |
| Деньги предыдущего клиента | Подошёл следующий клиент, прежние наличные ещё на столе |
| Приём инкассаторской сумки | В видимом фрагменте не наблюдается проверка документов инкассатора |
| Пересчёт без клиента | Деньги пересчитываются после ухода клиента |
| Посторонний в кассовой зоне | В рабочую зону входит дополнительный человек |
| Открытая дверь кассы | После входа кассира дверь остаётся открытой |
| Личные вещи на рабочем месте | В зоне работы с наличными видны напитки или личные вещи |

Это кандидаты для проверки человеком: ракурс, видимость всей процедуры и применимость нормы имеют значение. Человек в кадре сам по себе не доказывает отсутствие допуска.

Основания взяты из публичных актов РК: правила кассовых операций НБРК №231, охраны помещений НБРК №14 и требования к ИБ АРРФР №53. Для экрана открытая норма об автоблокировке служит ориентиром; обязанность блокировать его при уходе зависит от внутренних документов банка.

Связка: **наблюдаемый факт → условие правила → фрагмент и таймкод → источник**. Документы, пункты и оговорки: [каталог событий](src/forte/fast/catalog.py), [описание подхода](docs/fast-analyzer.md).

## Как это устроено

```text
React + TypeScript → FastAPI → PostgreSQL → worker
                                             ↓
                   PyAV → локальный Qwen3-VL → правила
                                             ↓
                       JSON + таймкоды + исходные JPEG
```

Основной профиль использует **Qwen3-VL-30B-A3B-Instruct** через локальный vLLM. Модель определяет области сцены и состояния объектов во времени, правила собирают события. Профиль демо дополнительно проверяет кандидатов моделью. API и обработчик работают отдельно, задания сохраняются в базе. [Лицензии компонентов](docs/submission/licenses.md).

## Запуск локально

Полный стек: **Linux или WSL2 с NVIDIA GPU**, Python 3, Docker Compose и NVIDIA Container Toolkit. Для текущей модели нужен GPU с BF16 и примерно 80 ГБ VRAM, минимум 70 000 MiB свободно. Веса в репозиторий не входят.

Из корня проекта:

```bash
cp deploy/.env.example deploy/.env
```

В `deploy/.env` заполните `FORTE_FAST_MODEL_REVISION`: проверенный 40-символьный commit SHA модели `Qwen/Qwen3-VL-30B-A3B-Instruct`. В `FORTE_FAST_MODEL_DIR` укажите доступный для записи абсолютный путь к весам. Затем:

```bash
bash deploy/bootstrap_fast_host.sh
```

Скрипт подготовит образы, скачает веса, создаст ключи и запустит модель, базу, API и worker. Первый запуск требует интернета и терпения. GPU кофе не пьёт, но время на разогрев берёт.

Откройте **[localhost:8080](http://127.0.0.1:8080)**. Введите ключ из `deploy/secrets/api_keys`, выберите `.mov` и нажмите **Начать проверку**. Готовность стека: `GET /readyz`.

Без контейнеров: [интерфейс и Vite](web/README.md#run), [CPU API и worker](README.technical.md#start-locally). Анализ всё равно требует локального сервиса модели. [Подробности GPU-запуска](deploy/README-fast.md).

## API для жюри

Адрес: **[forte-review-wd88a7vvt.gobrev.dev](https://forte-review-wd88a7vvt.gobrev.dev)**. Ключ передаётся жюри отдельно, оба метода требуют `X-API-Key`.

| Метод | Маршрут | Результат |
| --- | --- | --- |
| `POST` | `/api/v1/analyze` | Принимает `.mov` в multipart-поле `file`, возвращает `job_id` |
| `GET` | `/api/v1/jobs/{job_id}` | Возвращает `processing`, `done` или `failed` и готовый результат |

Пример для локального стека. В `FORTE_API_KEY` подставьте ключ из файла выше:

```bash
curl -H "X-API-Key: $FORTE_API_KEY" -F "file=@video.mov" \
  http://127.0.0.1:8080/api/v1/analyze
curl -H "X-API-Key: $FORTE_API_KEY" \
  http://127.0.0.1:8080/api/v1/jobs/JOB_ID
```

Готовый ответ содержит `verdict` (`violation` или `no_violation`) и `violations`. У события есть `type`, `timecode_sec`, `description`, `evidence_frames` с `timestamp_sec` и JPEG в `image_base64`. Без находок список пустой. По регламенту результат нужен за 5 минут. [Полный контракт](contracts/README.md).

## Наш путь

Начали с бодрого плана: загрузить видео и найти нарушение. Потом в плане появились очередь, таймкоды, нормативка и вопрос, почему модель опять смотрит не туда. К финишу собрали сервис, в котором у находки есть кадр, объяснение и возможность с ней поспорить. Недосып в архитектуру включать не стали.
